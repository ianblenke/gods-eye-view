- [ ] S2 (major) Decoder queue and drop rule: spec.md:129 "it drops delta frames while the queue of the decoder holds more than eight frames, until the next key frame". The same text is in design.md:62 and in the test name at src/layers/osh/videoPlayer.test.mjs:288. (1) The queue (`decodeQueueSize`) holds chunks that wait to decode, not frames. `frame` is also the decoder output. (2) "while ... until" has two readings: drop only while the queue is long, or start a drop that lasts until the next key message. The code (videoPlayer.js:129) and the test at videoPlayer.test.mjs:299 use the second reading. The first reading decodes delta chunks that refer to a dropped chunk. Propose: "When the decoder queue holds more than eight chunks, it drops each delta message until the next key message." Use the same text in design.md:62 and in the test name. In spec.md:129 and tasks.md:76 write "delta message", not "delta frame".
- [ ] S3 (major) Time stamp origin: spec.md:127 and design.md:60 say "the time stamp in microseconds from the first message". The code (videoPlayer.js:133 `originMs ??= ...`) and the test at videoPlayer.test.mjs:215 use the first message that the player decodes. A delta message before the first key message is not the origin, and a literal reading gives other chunk time stamps. "each later message" (spec.md:127) can also mean that the key message that starts the decoder is not decoded, but the test at videoPlayer.test.mjs:181 shows that it is. Propose: "it decodes each message from that key message on, as a key chunk or a delta chunk." Then add: "The time stamp of a chunk is in microseconds after the time stamp of the first decoded message." Use the same text in design.md:60.
