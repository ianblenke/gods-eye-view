Findings:
- [ ] S1 (major) A key message is defined two ways: design.md:9 "A key message also has an SPS and a PPS." D75 (design.md:52) and osh-080 (spec.md:107) say a key message is any message whose H.264 data has a NAL unit of type 5. The player text (design.md:62 "a key message with an SPS and a PPS", spec.md:152) and the tests (videoPlayer.test.mjs:147 and :372, "a key message with no PPS") treat a key message with no SPS or no PPS as a real case. Under design.md:9 that case cannot exist, so a reader cannot tell what the rule is. The same sentence also gives two rules for a delta message: "not a key message" and "its data has slices of type 1". A message with only an SEI unit follows the first rule and not the second. Propose: "A key message from a camera normally also has an SPS and a PPS, but it does not have to. The player decodes nothing until a key message has both. A delta message is a message that is not a key message. Its data normally has slices of type 1."
- [ ] S2 (major) osh-091 says the wrong thing about `live_busy`: spec.md:78 "`503` with `{error:'live_busy'}` when eight datastreams are open". Read literally, a client that joins one of the eight open datastreams gets 503. Main osh-068 (openspec/specs/osh/spec.md:637) and the test name (oshLive.test.mjs:1293) say only a ninth datastream or a seventeenth client gets 503. The same line says "the error code of the root", which names no code. osh-012 (main spec:87) gives two codes. The WHEN of osh-091 names a good request, but this line is about two failures, so the WHEN does not cover it. Propose: "the answer is `502` with `{error:'auth_failed'}` or `{error:'base_unresolved'}`, as `osh-012` says, when no root answers" and "the answer is `503` with `{error:'live_busy'}` for a ninth datastream or a seventeenth client, as `osh-068` says". Better, make these two lines their own scenario with a WHEN that names those two cases. Do the same in the synced spec (openspec/specs/osh/spec.md:716).
- [ ] S3 (major) A round-1 major finding is not corrected in the test names. Round-1 S2 asked for the same text in the spec, the design and the test name. The spec (spec.md:160) and the design (design.md:66) now say "when the decoder queue holds more than eight chunks, the player ignores each delta message until the next key message". The test at src/layers/osh/videoPlayer.test.mjs:288 still says "the player drops delta messages while the decoder queue holds more than eight frames". It uses `frames` for chunks, and `frame` now means only the decoded frame. "while" still has the reading that the player drops only while the queue is long, which is the wrong rule. Lines 299 and 324 use "the drop of delta messages". Propose for :288: "when the decoder queue holds more than eight chunks, the player ignores each delta message". For :299: "after the player ignores a delta message, it ignores each later delta message until the next key message". For :324: "a message that has no slice unit does not make the player ignore later delta messages".
- [ ] S4 (minor) The definition of a good message is split: spec.md:140-141 (osh-083). Line 140 says "a message is good when it has at least 12 bytes and its time stamp is a finite number". Line 141 then says "the length field of a good message equals its size minus 12". By line 140 alone, a message with a wrong length field is good, and line 141 then contradicts itself. Round-1 S4 proposed one sentence. Propose one line: "a message is good when it has at least 12 bytes, its length field equals its size minus 12, and its time stamp is a finite number".
- [ ] S5 (minor) Two readings in osh-084. (a) spec.md:158 "it reports the status `live` at the first drawn frame" can mean the first frame of the stream, or the first frame after each start. The code sets `live` back to false after a decoder error (videoPlayer.js:93), and the test at videoPlayer.test.mjs:404 checks `live` again. Propose: "it reports the status `live` at the first drawn frame after each start or reset". (b) spec.md:155 "it decodes each message from that key message on, as a key chunk or a delta chunk" says each message. The code ignores a message that has no slice NAL unit (videoPlayer.js:128), and the tests at :226 and :324 check it. Propose: "it decodes each message that has a slice NAL unit, from that key message on".
- [ ] S6 (minor) Small gaps in osh-079: spec.md:91 "the client receives one event `frame` for each good message" does not say which client. The test says "for each client". Propose: "each client of the entry receives one event `frame` for each good message". Line 101 "for ten minutes the video route ... answers `503`" does not say when the ten minutes start. Propose: "after that message, the video route for that datastream answers `503` with `{error:'live_unsupported'}` for ten minutes".
- [ ] S7 (minor) Nouns from verbs, and "leaves", in a new line of osh-081: spec.md:116 "a refusal or a close of one entry leaves the other entry of the same id open". Propose: "the other entry of the same id stays open when the hub refuses or closes one entry".
- [ ] S8 (minor) One thing has two names, `end` and `destroy`. The spec (spec.md:121), the design (design.md:94) and the proposal (proposal.md:15) say "destroys the response". The new tests say "ends a client" (oshLive.test.mjs:2067 and :2095) and "is never ended" (:2109, which is also passive). The mutation V17 in tasks.md:71 says "end a client". The comments say "the response ends" (osh.js:715) and "The route ends its response" (live.js:37). In osh-079 (spec.md:100) "ends the response" means `res.end()`, which writes the pending data and then closes. A reader can write `res.end()` for osh-090, and that keeps the 8 MiB buffer. Propose: "the video route destroys the response of a client that has more than 8388608 unwritten bytes, and the other client keeps its events". The second name: "the live route destroys the response of a client that has more than 8388608 unwritten bytes". The third name: "the route never destroys a response that reports no unwritten bytes". Use "destroy" in V17 and the two comments. The name at :2067 also does not say that the test checks a client at exactly 8388608 bytes, which stays. Add "and it keeps a client at exactly 8388608 bytes". In spec.md:121 write "and the hub removes that client", because "it" can mean the response.

In tasks.md:53 (task 4.8), "too many unwritten bytes" gives no number, and the bytes belong to the response, not the client. In tasks.md:47 "loses its response" and "keep theirs": write "the provider destroys its response, and the other clients keep their responses". In tasks.md:73 (V19) "after the destroy" is a verb used as a noun: write "V19: write the message after the provider destroys the response".
