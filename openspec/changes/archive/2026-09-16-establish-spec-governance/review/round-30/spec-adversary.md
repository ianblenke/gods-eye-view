- [ ] F1 major scripts/spec/lib/ledger.mjs:428 The ratchet command does not record the smaller gap of a band file when another count of the file is above its entry in the band. This is the usual result of a backfill test for an unchanged file. A new test calls a function that no test called before. V8 then counts the branches of that function, so the not-covered branch count can become larger (design.md tells this). I ran `ratchetLedger` with the `sameAsBase` of `gates.mjs` on the entry 20 lines, 3 branches, 2 functions (totals 100/10) and the gap 10 lines, 4 branches, 1 function (totals 104/10). The ledger kept 20/3/2 and the command wrote no history line. The check gave no error and no stale entry. A later change then removed the test, which gave the counts 20/3/2 again, and the check gave no error. Thus the backfill adds coverage, and a later change can remove all of it with no stop. This also disagrees with scenario `gap-ledger-028` (spec.md:355): "for an unchanged file with more not-covered branches and a covered branch count that is not smaller, THEN the command writes the larger branch count". With `sameAsBase: SAME`, the input of the 028 test (5/3/1 to 4/7/1) gets the 068 result, and the test at ledger.test.mjs:335 does not find this because it does not give `sameAsBase`. The limit `unchanged-band` (proposal.md:65) says "the ledger keeps the old count until the next ratchet run", but here the old count stays after the ratchet run too. The test for `gap-ledger-068` asserts this result for the "mixed" case (ledger.test.mjs:779). For a band file, write each smaller not-covered count. Keep the entry count only for a count above the entry in the band, and apply the `gap-ledger-028` rule when the covered count is not smaller. Then make `gap-ledger-028` and `gap-ledger-068` agree, and add a test with `sameAsBase` for the backfill case.

When no not-covered count is above the entry and the covered branch count is lower by at most the band (the total count is also lower), `largerInBand` is false. The command then writes the gap and a `totals changed` line. `compareWithBase` has no error for this, because it compares covered counts only when a not-covered count is above the base. In my experiment, 5 ratchet runs in a row, each against the ledger of the run before, took the covered branches from 97 to 72. No run gave a check error or a `compareWithBase` error. Do not write a covered count below the entry covered count for a band file, or name this in the limit `unchanged-band`.

- [ ] F4 minor Makefile:8 `tar -cf /tmp/copy.tar -T /tmp/files` reads each line of the file list as a possible option. In the image (GNU tar 1.34), a list line `--exclude=src` gave an archive with no `src/` files and status 0. A list line `-C` gave status 2. Git also quotes names with a tab or a `"` character, even with `core.quotepath=off`, and tar then stops because the file does not exist. Thus a tracked file with such a name can remove files from the copy with no message, or stop a correct change. Also, `{ grep … || true; }` ignores a grep error (status 2). The `ci-gates-007` test (ciFiles.test.mjs:29) checks each step with `includes`, so a change from `&&` to `;` between the steps does not make it fail. Use `git ls-files -z` with `tar --null --verbatim-files-from -T`, remove deleted files in a way that works with NUL-separated names, and assert in the test that `&&` joins the steps.
